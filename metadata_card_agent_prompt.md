# Excel-to-Queryable-Data Ingestion Pipeline — Build Specification

## What You Are Building

A Python system that takes messy Excel files, extracts tables from them, loads each table into a SQL-queryable store (Amazon Athena via Parquet files in S3), and generates a rich metadata card for each table. The metadata card is the core intellectual property — it is the primary mechanism by which a downstream LLM agent will decide which tables are relevant to a user's natural language question and how to query them.

The system does NOT normalize or rename columns. Each table keeps its original structure. The intelligence lives in the metadata card, not in the data transformation.

---

## Architecture Overview

```
Excel file (uploaded to S3)
    ↓
User provides rectangle coordinates (sheet name, start cell, end cell)
    ↓
Extraction: read rectangle with openpyxl → pandas DataFrame
    ↓
Storage: DataFrame → Parquet file → S3 → Athena table (via Glue Catalog)
    ↓
Metadata generation: LLM analyzes the extracted data and produces a metadata card
    ↓
Card stored alongside the data (JSON in S3)
    ↓
Over time: card accumulates usage data, learned mappings, confirmed relationships
```

---

## Key Design Decisions

1. **No normalization.** If a column is called "Client Vertical / Industry Segment", it stays that way. The metadata card describes the column in plain English so the LLM can understand it.

2. **Each table is independent.** There is no master schema. Each Excel rectangle becomes its own Athena table with its own metadata card. Cross-table relationships are discovered over time through usage, not enforced upfront.

3. **The metadata card has two halves.** A static half (created at ingestion, never changes) and a dynamic half (grows over time as the system is used). Both halves are what the LLM reads when deciding which tables to use.

4. **LLM-generated metadata is honest about mess.** If data quality is bad (mixed formats, missing values, abbreviations), the card says so explicitly. It does not pretend the data is clean.

## Class: TableCard

This is the central data structure. Everything in the system either creates a TableCard, reads a TableCard, or updates a TableCard.

### Static Half (set once at ingestion, never modified)

```python
class TableCard:

    # === IDENTITY ===
    # Where this data came from. Never changes.

    table_id: str
    # A unique identifier you assign, e.g. "tbl_00042"
    # Used as the Athena table name and the key for everything else

    source_file: str
    # Original Excel filename, e.g. "client_data.xlsx"

    source_sheet: str
    # Sheet name within the Excel file, e.g. "Sheet1"

    source_range: str
    # Cell range that was extracted, e.g. "B2:F45"

    ingestion_date: str
    # ISO date when this table was ingested, e.g. "2026-02-25"

    row_count: int
    # Number of data rows (excluding header)

    column_count: int
    # Number of columns


    # === COLUMN DEFINITIONS ===
    # Statistical profile of each column. Generated by code, not LLM.
    # This is objective — just facts about the data.

    columns: list[ColumnProfile]
    # See ColumnProfile class below


    # === LLM-GENERATED DESCRIPTION ===
    # The LLM reads the first ~20 rows and the column profiles,
    # then writes these three fields.

    description: str
    # Plain English explanation of what this table is.
    # Example: "A master client roster containing 43 companies with
    # their annual revenue, industry classification, geographic region,
    # and relationship status. Appears to be maintained by the business
    # development team as a primary client reference list."

    purpose: str
    # What kinds of questions this table can answer.
    # Example: "Client segmentation, market sizing, revenue analysis
    # by industry or geography, identifying active vs dormant relationships"

    caveats: str
    # Warnings about data quality, inconsistencies, things that could
    # cause wrong query results.
    # Example: "Two rows have null Status values. Industry values are
    # not standardized — 'Financial Technology' and 'Fintech' both appear
    # and likely refer to the same category."


    # === ENTITIES ===
    # What real-world things does this table describe?

    entities: list[EntityProfile]
    # See EntityProfile class below


    # === CROSS-REFERENCE HINTS ===
    # Which columns in this table might connect to other tables?
    # These are guesses at ingestion time. They get confirmed or
    # rejected over time in the dynamic half.

    cross_references: list[CrossReference]
    # See CrossReference class below


    # === QUERY PATTERNS ===
    # Pre-generated example SQL queries that work against this
    # specific table's actual column names.

    query_patterns: list[QueryPattern]
    # See QueryPattern class below
```

### Dynamic Half (grows over time with usage)

```python
    # === USAGE LOG ===
    # Every time a user asks a question and the system considers this
    # table, a log entry is created — whether the table was selected or not.

    usage_log: list[UsageEntry]
    # See UsageEntry class below


    # === LEARNED TAGS ===
    # Tags that describe what this table is good for.
    # Initial tags come from the LLM at ingestion.
    # Learned tags come from observing what queries this table
    # successfully answers over time.

    tags_initial: list[str]
    # Set at ingestion, e.g. ["clients", "revenue", "industry"]

    tags_learned: list[str]
    # Added over time, e.g. ["market sizing", "TAM", "fintech analysis"]


    # === RELIABILITY SCORE ===
    # Track record of how well this table serves queries.

    query_success_rate: float
    # Percentage of generated SQL that ran without Athena errors (0.0 to 1.0)

    user_satisfaction_rate: float
    # Percentage of results that got positive or neutral feedback (0.0 to 1.0)

    total_queries: int
    # How many times this table has been used in a query


    # === LEARNED VOCABULARY MAPPINGS ===
    # The system learns how users refer to things in this table.
    # Example: user says "fintech", system learns that maps to
    # the "Industry" column with values ["Financial Technology", "Fintech"]

    learned_mappings: list[VocabularyMapping]
    # See VocabularyMapping class below


    # === CONFIRMED RELATIONSHIPS ===
    # Cross-table joins that have actually been tested and work.
    # These start as cross_reference hints (static half) and get
    # promoted to confirmed relationships after successful joins.

    confirmed_relationships: list[ConfirmedRelationship]
    # See ConfirmedRelationship class below
```

## Supporting Classes

### ColumnProfile

```python
class ColumnProfile:
    name: str
    # The exact column header as it appears in the Excel file
    # e.g. "Client Vertical / Industry Segment"

    data_type: str
    # One of: STRING, INTEGER, FLOAT, DATE, BOOLEAN, MIXED
    # MIXED means the column has inconsistent types (some text, some numbers)
    # Determined by scanning actual values, not by guessing

    unique_values: int
    # How many distinct values exist in this column

    sample_values: list[str]
    # A few example values, e.g. ["Acme Corp", "Beta Health", "Gamma Retail"]
    # For columns with few unique values (< 20), list ALL values.
    # For columns with many unique values, list 5-10 representative samples.

    all_values: list[str] | None
    # If unique_values < 20, this is the complete list of all distinct values.
    # This is critical for the LLM — if it knows all possible values of "Status"
    # are ["Active", "Prospect", "Dormant"], it can write exact WHERE clauses.
    # If unique_values >= 20, this is None (too many to list).

    null_count: int
    # How many cells in this column are empty/null

    # Numeric stats (only populated if data_type is INTEGER or FLOAT)
    min_value: float | None
    max_value: float | None
    mean_value: float | None

    # Format warnings (populated if the data is messy)
    format_warnings: list[str] | None
    # e.g. ["Values use mixed formats: '2.5M', '900K', '1,200,000'"]
    # e.g. ["Contains '???' as a placeholder for unknown values"]
    # e.g. ["Some values have leading/trailing whitespace"]
```

### EntityProfile

```python
class EntityProfile:
    name: str
    # The real-world thing this entity represents, e.g. "Client", "Deal", "Partner"

    is_primary: bool
    # True if this entity has one row per instance in the table.
    # A client table where each row is a different client → Client is primary.
    # A deals table where Acme appears in 3 rows → Client is NOT primary in that table.

    identified_by: str
    # Which column identifies this entity, e.g. "Client Name"

    cardinality: str
    # How the entity maps to rows.
    # "one per row" — each row is a unique instance
    # "many per row" — not applicable (would be unusual)
    # "one to many" — one entity can appear in multiple rows (e.g. client in deals table)

    attributes: list[str]
    # Which other columns describe this entity.
    # e.g. ["Annual Revenue", "Industry", "Region", "Status"]

    description: str
    # LLM-generated note about this entity in context of this table.
    # e.g. "Each client appears exactly once. Revenue values are in USD, not abbreviated."
```

### CrossReference

```python
class CrossReference:
    column: str
    # Which column in THIS table might connect to other tables
    # e.g. "Client Name"

    likely_entity_type: str
    # What kind of entity this column refers to
    # e.g. "Client" — meaning other tables that also have client data

    match_quality: str
    # How reliable a join would be
    # "exact" — values should match directly across tables
    # "fuzzy" — values are similar but may differ (abbreviations, formatting)
    # "unknown" — can't tell without seeing the other tables

    notes: str
    # Any caveats about matching
    # e.g. "Uses abbreviated names ('Acme' not 'Acme Corp') — may need fuzzy matching"
```

### QueryPattern

```python
class QueryPattern:
    natural_language: str
    # The kind of question this query answers, in plain English
    # e.g. "Total revenue by industry"

    sql: str
    # The actual SQL query using this table's real column names
    # e.g. SELECT "Industry", SUM("Annual Revenue") FROM tbl_00042 GROUP BY "Industry"

    warnings: str | None
    # Any caveats about this query
    # e.g. "SUM won't work on '$ Val' column because values are text like '2.5M'"
```

### UsageEntry

```python
class UsageEntry:
    date: str
    # When this entry was created

    user_query: str
    # What the user asked, in natural language

    was_selected: bool
    # Whether this table was selected as relevant for the query

    selection_reason: str
    # Why the table was selected (or why it wasn't)
    # e.g. "Contains client revenue data with industry classification"
    # e.g. "Table contains client attributes, not deal/pipeline data"

    sql_generated: str | None
    # The SQL query that was generated (only if was_selected=True)

    query_succeeded: bool | None
    # Whether the SQL ran without error in Athena

    user_feedback: str | None
    # "thumbs_up", "thumbs_down", or None (no feedback given)
```

### VocabularyMapping

```python
class VocabularyMapping:
    user_term: str
    # What the user said, e.g. "fintech"

    maps_to_column: str
    # Which column this maps to, e.g. "Industry"

    maps_to_values: list[str]
    # Which column values match, e.g. ["Financial Technology", "Fintech"]

    confidence: str
    # "high" (confirmed multiple times), "medium" (confirmed once), "low" (inferred)

    times_confirmed: int
    # How many successful queries have used this mapping
```

### ConfirmedRelationship

```python
class ConfirmedRelationship:
    this_column: str
    # Column in this table, e.g. "Client Name"

    other_table_id: str
    # The table_id of the other table, e.g. "tbl_00058"

    other_column: str
    # Column in the other table, e.g. "Acct"

    join_type: str
    # "exact" (values match directly) or "fuzzy" (need approximate matching)

    match_rate: float
    # What percentage of values in this column found a match in the other table
    # e.g. 0.87 means 87% of client names matched

    mapping_examples: list[dict]
    # Concrete examples of how values map
    # e.g. [{"this": "Acme Corp", "other": "Acme"}, {"this": "Beta Health", "other": "Beta Health"}]

    times_used: int
    # How many queries have used this join successfully
```

## Functions To Build

### Phase 1: Ingestion (creates the static half)

#### Function: read_rectangle

```
Input:  file_path (str), sheet_name (str), start_cell (str), end_cell (str)
Output: pandas DataFrame

Logic:
    1. Open Excel file with openpyxl (data_only=True to get computed values, not formulas)
    2. Navigate to the specified sheet
    3. Convert start_cell and end_cell to row/column numbers
       e.g. "B2" → row=2, col=2 and "F45" → row=45, col=6
    4. Read all cells in that rectangle
    5. First row becomes column headers
    6. Remaining rows become data
    7. Return as DataFrame
```

#### Function: profile_columns

```
Input:  DataFrame
Output: list[ColumnProfile]

Logic:
    For each column in the DataFrame:
        1. Count unique values, null values
        2. Determine data type by inspecting actual values:
           - If all non-null values are numeric → INTEGER or FLOAT
           - If all non-null values parse as dates → DATE
           - If mixed → MIXED (flag this as a warning)
           - Otherwise → STRING
        3. If numeric: compute min, max, mean
        4. If unique values < 20: store all distinct values in all_values
        5. Always store 5-10 sample values
        6. Detect format warnings:
           - Mixed number formats ("2.5M" and "1,200,000" in same column)
           - Placeholder values ("???", "N/A", "TBD", "-")
           - Leading/trailing whitespace
           - Inconsistent casing ("Active" vs "active" vs "ACTIVE")
```

#### Function: create_athena_table

```
Input:  DataFrame, table_id (str), s3_bucket (str)
Output: Athena table name, column definitions

Logic:
    1. Convert DataFrame to Parquet file
    2. Upload Parquet to s3://{bucket}/processed/{table_id}/{table_id}.parquet
    3. Generate and execute CREATE EXTERNAL TABLE statement in Athena
       using the column names and types from profile_columns
    4. Return the table name and column definitions
```

#### Function: generate_description

```
Input:  DataFrame (first 20 rows), list[ColumnProfile]
Output: description (str), purpose (str), caveats (str)

Logic:
    1. Format the column profiles and sample data into a prompt
    2. Send to Claude (via Bedrock) with instructions:
       "You are analyzing a data table extracted from an Excel file.
        Based on the column names, data types, sample values, and
        statistics provided, write:
        1. A plain English description of what this table contains
           and who likely maintains it
        2. What kinds of questions this table could answer
        3. Any warnings about data quality, inconsistencies, or
           limitations that would affect query accuracy"
    3. Parse Claude's response into the three fields
```

#### Function: extract_entities

```
Input:  DataFrame (first 20 rows), list[ColumnProfile], description, purpose, caveats
Output: list[EntityProfile], list[CrossReference]

Logic:
    1. Send all inputs to Claude with instructions:
       "Given this table and its description, identify:
        1. The primary entity (the main thing each row represents)
        2. Any secondary entities (things that appear as attributes
           but are entities in their own right)
        3. For each entity: which column identifies it, what other
           columns describe it, and what is the cardinality
        4. Which columns might contain references to entities that
           exist in OTHER tables (e.g. a client name column in a
           deals table probably refers to clients that have their
           own table somewhere). For each, assess whether matching
           would be exact or fuzzy."
    2. Parse response into EntityProfile and CrossReference objects
```

#### Function: generate_query_patterns

```
Input:  table_id, list[ColumnProfile], description, purpose, caveats, list[EntityProfile]
Output: list[QueryPattern]

Logic:
    1. Send all inputs to Claude with instructions:
       "Write 5-8 example SQL queries that someone might realistically
        run against this table. Requirements:
        - Use the EXACT column names from the table (quoted if they
          contain spaces or special characters)
        - Use the table name {table_id}
        - Cover different query types: filtering, aggregation, grouping,
          sorting, counting
        - If any column has data quality issues that would affect a
          query, include a WARNING comment in the SQL
        - For each query, write a one-line natural language description
          of what question it answers"
    2. Parse response into QueryPattern objects
```

#### Function: build_card

```
Input:  All outputs from the above functions
Output: TableCard (with static half populated, dynamic half empty)

Logic:
    1. Assemble all static fields into a TableCard object
    2. Initialize dynamic fields to empty:
       - usage_log = []
       - tags_initial = (extract from description/purpose using simple keyword extraction)
       - tags_learned = []
       - query_success_rate = 0.0
       - user_satisfaction_rate = 0.0
       - total_queries = 0
       - learned_mappings = []
       - confirmed_relationships = []
    3. Serialize to JSON
    4. Store in S3 at s3://{bucket}/metadata/{table_id}/card.json
    5. Return the TableCard
```

### Phase 2: Query Time (reads the static half, updates the dynamic half)

These functions are for the downstream query agent. You do not need to build
them now, but the TableCard structure must support them.

#### Function: select_tables

```
Input:  user_query (str), all TableCards
Output: list of selected TableCards with selection reasons

Logic:
    1. The LLM reads all card descriptions, purposes, entity lists,
       and learned tags
    2. For each card, the LLM decides: is this table relevant to
       the user's question? Why or why not?
    3. Returns the selected cards and reasons
    4. Logs a UsageEntry on EVERY card (selected or not)
```

#### Function: generate_query

```
Input:  user_query (str), selected TableCard(s)
Output: SQL query string

Logic:
    1. The LLM reads the selected card's column definitions,
       query patterns, caveats, and learned vocabulary mappings
    2. Generates SQL using the exact column names and table name
    3. If multiple tables are selected and confirmed_relationships
       exist between them, generates a JOIN query
    4. Returns the SQL
```

#### Function: update_card_after_query

```
Input:  TableCard, UsageEntry, query_result, user_feedback
Output: Updated TableCard

Logic:
    1. Append UsageEntry to usage_log
    2. Update query_success_rate and user_satisfaction_rate
    3. Increment total_queries
    4. If user_feedback indicates a vocabulary correction
       (e.g. user said "fintech" and it worked), add or update
       a VocabularyMapping
    5. If a cross-table join succeeded, promote the CrossReference
       hint to a ConfirmedRelationship
    6. If this query type has succeeded multiple times, consider
       adding a new learned tag
    7. Save updated card to S3
```

## Implementation Order

### Build First (Core ingestion):
1. `ColumnProfile` and `profile_columns` — pure Python, no LLM, testable immediately
2. `read_rectangle` — pure openpyxl, testable with any Excel file
3. `create_athena_table` — needs AWS credentials, but straightforward boto3 calls
4. `TableCard` class with serialization to/from JSON
5. `generate_description` — first LLM call, needs Bedrock access
6. `extract_entities` — second LLM call
7. `generate_query_patterns` — third LLM call
8. `build_card` — assembles everything

### Build Second (Query time — separate agent):
9. `select_tables` — reads cards, picks relevant ones
10. `generate_query` — writes SQL from selected cards
11. `update_card_after_query` — updates dynamic half

### Build Third (Learning loop):
12. Vocabulary mapping updates
13. Relationship confirmation
14. Tag learning from usage patterns
15. Reliability scoring

## AWS Services Required

- **S3**: Two buckets — one for raw Excel files, one for processed Parquet + metadata cards
- **Athena**: Serverless SQL engine, queries Parquet files in S3
- **Glue Data Catalog**: Metadata registry that tells Athena what tables exist (created automatically by CREATE TABLE statements run in Athena)
- **Bedrock (Claude)**: For generating descriptions, entities, query patterns at ingestion time, and for text-to-SQL at query time
- **Lambda or EC2**: To run the ingestion pipeline (Lambda for small files, EC2 for large batches)

## Testing Strategy

For each function, create a test with a small Excel file (3-5 rows) that covers:

1. **Clean data** — all columns have consistent types and no nulls
2. **Messy data** — mixed formats ("2.5M" and "900K"), placeholder values ("???", "N/A"), abbreviations ("CW" for "Closed Won")
3. **Missing data** — null cells, empty columns
4. **Pivot layout** — time periods as columns, entities as rows

Verify that:
- ColumnProfile correctly identifies MIXED type when formats are inconsistent
- Format warnings are generated for all known messy patterns
- LLM descriptions are honest about data quality issues (not optimistic)
- Query patterns use exact column names from the data (quoted when they contain spaces)
- Query patterns include warnings when operations would fail on messy columns
